# Topic 1: Introduction to JPA and Hibernate

With JDBC (Session 10) we wrote every SQL statement and mapped every column by hand. An **ORM**
(Object-Relational Mapper) does that work: you describe how a class maps to a table once, then save
and load **objects**; the ORM writes the SQL.

| Name | What it is |
|---|---|
| **JPA** (Jakarta Persistence) | The standard: annotations (`@Entity`, `@Id`, `@OneToMany`...) and interfaces (`EntityManager`) in `jakarta.persistence` |
| **Hibernate** | The most used **implementation** of JPA; the one Spring Boot uses |
| **Spring Data JPA** | Spring's layer on top: repository **interfaces** whose code Spring generates |

```
your code ──▶ Spring Data repository (StudentRepository)  ──▶ JPA EntityManager ──▶ Hibernate ──▶ JDBC ──▶ database
               findByEmail("asha@example.com")                                   writes the SQL
```

All of it comes with one dependency: `spring-boot-starter-data-jpa` (+ a JDBC driver).

## What Hibernate does for you

```java
Student kiran = students.save(new Student("Kiran", "kiran@example.com"));   // INSERT, id filled in
students.findByEmail("ravi@example.com");                                   // SELECT ... WHERE email = ?
student.setName("New name");   // inside a transaction: UPDATE at commit, no save() call needed
```

It even creates the tables from the classes (`spring.jpa.hibernate.ddl-auto=create-drop`). Real
generated DDL for `Student`:

```sql
create table student (
    id bigint generated by default as identity,
    profile_id bigint unique,
    email varchar(255) not null unique,
    ...
```

`ddl-auto` is for learning and tests. Production uses migration scripts (Flyway, Liquibase) and
`ddl-auto=validate`, so schema changes are reviewed and versioned.

## Seeing the SQL

[`application.properties`](../../src/main/resources/application.properties) logs every statement:

```properties
logging.level.org.hibernate.SQL=DEBUG
spring.jpa.properties.hibernate.format_sql=true
```

Always look at the SQL while learning: an innocent-looking line can run many queries (topic 4, N+1).

## The persistence context ("first-level cache")

Inside one transaction, Hibernate keeps every entity it loaded in its **persistence context**:

- Loading the same id twice returns the **same object** without a second query.
- Changes to those **managed** objects are found at commit (**dirty checking**) and written as UPDATEs.
- `entityManager.flush()` writes pending changes now; `clear()` forgets the cached objects. The tests
  use both to force a real reload from the database.

## JPA vs JDBC

| | JDBC / JdbcTemplate | JPA / Hibernate |
|---|---|---|
| You write | All SQL + row mapping | Entity mappings; SQL only for special queries |
| Relationships | JOINs by hand | `@OneToMany`, `@ManyToMany`... navigated as fields |
| Control & speed | Full control | Convenient; you must watch the generated SQL |
| Good for | Reports, bulk operations, tuned queries | Domain models with relationships, typical CRUD |

Many applications use both.

## Interview questions

- **JPA vs Hibernate?** Specification vs implementation.
- **What is an ORM?** A layer mapping objects to tables and generating SQL.
- **What is the persistence context?** The set of managed entities in a transaction: identity map + dirty checking.
- **What does `ddl-auto` do? Which value in production?** Generates the schema; `validate` or `none` (use migrations).
- **`save()` vs dirty checking?** `save` for new entities; changes to managed entities are saved automatically at commit.
