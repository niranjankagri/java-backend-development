# Topic 3: Database schema and entity design

## The entities

```
app_user 1 ──── * listing 1 ──── * booking * ──── 1 app_user
  (a host has listings)   (a listing has bookings)   (a guest has bookings)
                    │
                    1 ──── * listing_amenity
```

| Entity | Key decisions |
|---|---|
| [`AppUser`](../../../airbnb-backend/src/main/java/jbdl/airbnb/users/AppUser.java) | no host/guest account types: a user is a host because they own listings; email unique |
| [`Listing`](../../../airbnb-backend/src/main/java/jbdl/airbnb/listings/Listing.java) | price `BigDecimal(10,2)`; amenities as a set of enums in their own table; `active` instead of deleting; index on `city` |
| [`Booking`](../../../airbnb-backend/src/main/java/jbdl/airbnb/bookings/Booking.java) | dates as `LocalDate` (a day, no time zone); total price **stored**; status CONFIRMED/CANCELLED; check constraint on the dates; index on listing + dates |

## The schema Hibernate generates

From the entities, at start-up (real output, H2, `logging.level.org.hibernate.SQL=debug`):

```sql
create table app_user (id bigint generated by default as identity, name varchar(100) not null,
    email varchar(150) not null unique, primary key (id))
create table listing (active boolean not null, bedrooms integer not null, max_guests integer not null,
    nightly_price numeric(10,2) not null, created_at timestamp(6) with time zone not null,
    host_id bigint not null, id bigint generated by default as identity, city varchar(80) not null,
    title varchar(120) not null, description varchar(2000), primary key (id))
create table listing_amenity (listing_id bigint not null, amenity enum ('AIR_CONDITIONING','KITCHEN',
    'PARKING','POOL','WASHING_MACHINE','WIFI','WORKSPACE'), unique (listing_id, amenity))
create table booking (check_in date not null, check_out date not null, guests integer not null,
    total_price numeric(12,2) not null, created_at timestamp(6) with time zone not null,
    guest_id bigint not null, id bigint generated by default as identity, listing_id bigint not null,
    status enum ('CANCELLED','CONFIRMED') not null, primary key (id),
    constraint ck_booking_dates check (check_out > check_in))
create index idx_booking_listing_dates on booking (listing_id, check_in, check_out)
create index idx_listing_city on listing (city)
alter table if exists booking add constraint FK... foreign key (guest_id) references app_user
alter table if exists booking add constraint FK... foreign key (listing_id) references listing
alter table if exists listing add constraint FK... foreign key (host_id) references app_user
alter table if exists listing_amenity add constraint FK... foreign key (listing_id) references listing
```

## Decisions explained

**A stay is half-open: check-in day included, check-out day not.**
[`DateRange`](../../../airbnb-backend/src/main/java/jbdl/airbnb/bookings/DateRange.java) holds the rule:
20 to 23 December is 3 nights (20, 21, 22), and a guest can check in on the 23rd, the day the previous
one leaves. Two stays overlap when **each starts before the other ends**:

```java
public boolean overlaps(DateRange other) {
    return checkIn.isBefore(other.checkOut) && checkOut.isAfter(other.checkIn);
}
```

That one line covers every case (partly overlapping, inside, around, the same dates). Search uses the
same rule in SQL (topic 5). `DateRange` refuses a stay of 0 nights in its constructor, and the
database refuses it again with `check (check_out > check_in)`: if a bug ever skipped the Java check,
the database would still say no.

**The price is copied into the booking.** If Asha raises her price next month, Ravi's booking keeps the
10,500 he agreed to. Storing a value that could be computed is right when the value must not change
later.

**Listings are deactivated, never deleted.** Old bookings point to them (foreign key), and a guest's
history must still show where they stayed.

**Amenities: `@ElementCollection`.** A set of simple values, not entities with their own id: Hibernate
stores them in `listing_amenity` (one row per amenity, `unique (listing_id, amenity)`), with no extra
entity class. Stored by name (`@Enumerated(STRING)`), so adding an amenity in the middle of the enum
changes nothing in existing data.

**Indexes for the questions we ask.** Search always filters by city (`idx_listing_city`), and the
availability check reads bookings by listing and dates (`idx_booking_listing_dates`).

**LAZY relations.** `Listing.host` and `Booking.listing/guest` are loaded only when used.
`listing.getHost().getId()` does not even need the host row: a lazy reference knows its id.

## Interview questions

- **How do you check whether two date ranges overlap?** `a.start < b.end && b.start < a.end` (with an
  exclusive end). Drawing the cases shows that all overlaps meet it and no others do.
- **Why store the total price instead of computing it?** It is a fact of the past (the agreed price);
  the inputs (the nightly price) may change.
- **Soft delete vs. hard delete?** Soft delete (a flag) keeps history and foreign keys intact; queries
  must then filter on the flag (`l.active = true` in search).
- **Why a CHECK constraint when the Java code already checks?** Defence in depth: every writer of the
  table (another service, a script, a bug) is held to the rule.
